# Security policy

Bluestaq Limited. UNCLASSIFIED. Light Bee V1.0. The threat model and controls are in `docs/BRIEF.md` section 8; this file records the accepted risks and the limits of the local controls, so none of them is left implicit.

## Accepted risks

| Risk | Why it is accepted | Compensating control |
|---|---|---|
| Sessions, and the credentials in them, are lost on a pod restart | Nothing is written to disk by design; the analyst signs in again | Sessions expire after 8 hours idle regardless |
| Sessions are bound to a browser cookie, not the App Store identity | Whether the App Store passes the signed-in identity is TBC, re-verify | Random 256-bit, HttpOnly, Secure, SameSite=Strict cookie; session cap |
| A base-image CVE with no upstream fix may appear at Container Scan | The base tag floats so each build takes the latest patches | Alpine base (Debian had 59 won't-fix highs); fail-closed OS upgrade; SQLite, pip and the apk binary removed; flattened image; local grype scan before upload shows no critical or high (`docs/evidence/container-scan-1.0.0.md`) |
| BusyBox applets that can reach the network (`wget`, `nc`) are in the Alpine image, which Debian slim did not carry | They are part of the single BusyBox binary the base needs, and an attacker with code execution already has Python | Non-root user, no setuid bits, no package manager, nothing writable outside `/tmp` and `/var/tmp` |

## Service controls (Phase 3)

* **Sessions**: credentials live only in the session object in process memory; the browser holds a random 256-bit token in a `__Host-lightbee` cookie (Secure, HttpOnly, SameSite=Strict, path /, no domain); the server keys sessions by the token's SHA-256. Idle expiry 8 hours, cap 16 sessions, sign-out drops the session and its cached data at once. Credentials are checked with one small UDL read at sign-in.
* **Cross-site requests**: every state-changing call needs the `X-Light-Bee: 1` header, which a cross-site form cannot send and a cross-site script cannot send without a CORS preflight this app never answers; with the SameSite=Strict cookie that closes request forgery.
* **Isolation**: a run belongs to its session; another session asking for it gets 404. One run at a time per session; each run has its own UDL client and throttle.
* **Input**: every body is a pydantic model with `extra="forbid"`, strict types and explicit bounds (NORAD ID 1 to 99999, change date 2000-01-01 to today, window 1 to 31 days, provider pattern, history 0.25 to 2 years, screening 1 to 2,000 km, at most 50,000 selected times inside the run's window). Validation errors name the field, never echo the value.
* **Request size and rate**: every request body is capped at 1 MiB before routing or parsing (declared or streamed; 413). A broad limit counts every request from a live session (the cookie must name a session the store holds), 600 a minute per session and 3,000 across sessions; requests without a live session are not counted, so anonymous or random-cookie floods cannot use up analysts' room. `/`, `/static/*` and the health probes are never limited. The limiter reads cookies with Starlette's own parser, part by part across every Cookie header, so it sees every spelling the routes accept (spaces around the name, quoted values); a request carrying more than one session cookie is refused (400), so the limiter and the routes always read the same cookie. Volume-based denial of service by anonymous traffic (large bodies to the sign-in or 401 paths) is not limited in the app: that needs ingress rate limiting or a trustworthy client address (TBC, re-verify with the platform team); measured, the probes stayed under 170 ms at about 90 MB/s of anonymous 1 MB bodies. Then two tiers per kind: runs 20 and 60 an hour, scans 120 and 600 an hour (one at a time per session). Failed sign-ins only are counted, 10 per username (hashed) and 100 service-wide per 15 minutes, which bounds the UDL checks a stranger can cause; a username that has signed in successfully since the process started is held only by its own count, so a flood of random usernames cannot lock returning analysts out. Accepted residuals: during such a flood an analyst signing in for the first time since a restart waits up to 15 minutes, and someone who knows a username can hold that one account for 15 minutes with 10 wrong passwords (the UDL applies its own lockout too). Keying by client address would narrow both but needs the ingress to confirm a trustworthy forwarded-address header (TBC, re-verify with the platform team). Owner's decision (Charlie, 11 November 2026): the Bluestaq App Store is reachable by staff only, so the first-sign-in hold, the known-username hold and anonymous volume floods are accepted as they stand; Plotly 2.35.3 is accepted subject to a known-vulnerability check in Phase 5. Scans stop at 15 s and close-approach sweeps at 30 s.
* **Ending a session ends its work**: sign-out or expiry cancels the session's run at its next step (before its first UDL read if it has not started), and a run finishing afterwards cannot refill the session. A new sign-in from the same browser replaces its old session. Cached data across all sessions is held to a 900 MB budget, oldest first; a finished run whose data is released keeps its id and tells the analyst to run it again (410).
* **Audit**: one line per run and per scan on the `lightbee.audit` logger: a 12-character hash of the session key, NORAD ID, window, provider, counts and timings. Never a credential or UDL username (a test checks).
* **Logging (1.1)**: every line is one JSON object on standard output in the App Store standard shape; nothing goes to standard error. Lines written while a request is handled carry its `X-Request-Id` and the platform gateway's `X-Auth-Request-Email` (the analyst's App Store identity, which the standard requires; never the UDL username), each validated to a plain bounded label first and ignored if sent more than once; a background run carries the request ID of the request that started it. One line per request names the method, the path (never the query string), the status and the time taken; probes and static files are not logged. No other header, cookie, token, credential or query string reaches a line: the HTTP client's own INFO lines, which print full request URLs, are held to WARNING, and uvicorn's access log, which prints the query string, is off (tests check each, one of them against the real server over HTTP).
* **`user.email` is gateway-asserted, not authenticated by Light Bee**: it is used for attribution in the log only, never for access, and the audit's authoritative actor stays the session hash. It is trustworthy only if the platform gateway strips or overwrites a client-supplied `X-Auth-Request-Email`: TBC, re-verify with the platform team.
* **Content security policy**: `default-src 'none'`, scripts and styles from self only, no `unsafe-inline` and no `unsafe-eval`. Plotly runs under it (browser-tested): it is given a same-origin stylesheet (`plotly-rules.css`, id `plotly.js-style-global`) to write its rules into, its own toolbar is off, and only SVG traces are used. Plotly's attempts to set inline `style` attributes are blocked; the only effect is on default sizing, which the page sets explicitly. All server text reaches the page through `textContent` or as Plotly data, and Plotly titles and annotations are HTML-escaped server-side.
* **Exports**: PNGs are made in the browser and carry the marking (the controls on every record used), the test and evaluation banner, the object, window, sources and generation time. The scan CSV carries the marking on its first line and neutralises any cell that could start a spreadsheet formula.

## UDL client limits, recorded

* **Response size**: each response body is streamed against a 16 MiB cap and a page may not hold more records than were asked for; an oversized answer is divided, never parsed whole.
* **Environment**: the HTTP client ignores proxy and certificate environment variables (`trust_env=False`). If the App Store requires an egress proxy, it must be configured through validated settings (TBC, re-verify with the platform team).
* **Catalogue numbers** are limited to 1 to 99999 (owner's decision for V1). Alpha-5 TLEs (six-digit numbers) are not decoded.
* **UDL rejection detail**: a 4xx reply's first 1 KB is kept for diagnosis as `UdlRequestError.detail`, never in the message. The client's own credentials (the header, its token, the username, the password) and anything credential-shaped (an auth scheme and token, a credential-named field and value) are replaced with `[REDACTED]` before it is trimmed to 300 printable ASCII characters, and a body cut at the byte limit loses its last word. Before redaction the text is URL-, HTML- and JSON-unescaped (twice), then any 8-character fragment of the token, the password or `user:password`, any shorter secret of 3 or more characters in full, and any 16-character opaque run mixing letters and digits or carrying `+/=%` is replaced. `\uXXXX` and backslash escapes are undone too. Accepted limits: a password of 1 or 2 characters cannot be redacted without destroying the text (UDL passwords are far longer); and an upstream that decodes the Basic header and then changes the password's case, spaces out its characters, or re-encodes it (UTF-16, a line break every few characters) can defeat redaction. Each needs the UDL itself to echo the decoded password, and the detail is shown only to developer tools. It must still be escaped wherever it is rendered.
* **Screen work bounds**: elsets with an epoch outside the window asked for are refused; the screen takes at most 3,000 candidates, 4,000 selected instants and a 31 day window, and propagates 200 objects at a time.
* **Markings**: ASCII only (a lookalike letter or Unicode space is refused); only `U` or `UNCLASSIFIED`, alone or with the PR-MRKT, PR-EXO-OBS, DS-NSFCTC-OBS or PR-KBR-ELSETS controls (accepted by the owner, 10 November 2026), pass. Any other control, a second `//` block or an empty control is refused and counted. Products carry the controls of the records kept.
* **Credentials in memory** are readable by anything running in the process (the Basic header sits in the HTTP client's default headers). Nothing serialises or logs them; sessions in Phase 3 must keep it that way.

## Limits of the local controls

* **Secret scanning is pattern-based and line-based** (with wrapped assignments joined), shared by the gate, the packager and the pre-write hook (`tools/secret_patterns.py`, mirrored in `.claude/hooks/secret-scan.mjs`; `tools/prove_gates.py` checks both against the same 100 cases and against each other). It catches accidental commits, not deliberate hiding. Known misses, accepted:
  * a credential split into fragments, encoded, or assembled at run time (a hostile committer is outside this control's scope; review and the platform's Secret Detection stage are the backstops);
  * quoted values shorter than 6 characters;
  * unquoted values in Python or web sources (unquoted values are scanned in configuration files, Markdown and the Dockerfile only);
  * a credential assigned to a name that says nothing about it (`x = "..."`), or to a name ending in a label word such as `_NAME`, `_URL` or `_MESSAGE`;
  * an error body that uses a credential word as its key (`{"credentials": "missing or rejected"}`): use a neutral key such as `error`.
  * a name ending in a label word whose value is prose, a URL, a path, a selector, a header or scheme word, or a lowercase identifier (`UDL_PASSWORD_MESSAGE = "correct horse battery staple"` passes): the label exemption is value-gated, so a mixed-character value under a label name still fires;
  * an interpolated f-string (`f"{a}:{b}"`), which is assembled from other values.
  * a label-named value containing any `/` or a single capitalised word (`UDL_PASSWORD_HINT = "aB3/xY9+zQ=="`, `UDL_PASSWORD_MODE = "Hunter"`), because rate strings such as `"10/minute"` and scheme words must pass;
  * `COOKIE_KEY` and a bare `BEARER` name (`cookie_key = "lb_session"` is a common non-secret name);
  * an f-string with a literal credential head and an interpolated tail (`f"Hunter2{suffix}"`);
  * `session_id = "<hex>"`: the name does not say credential, though in this app a session id is one. Tests use obviously fake session values;
  * Playwright's locator style (`page.locator("#password").fill("...")`, `get_by_label(...).fill(...)`) and selectors such as `input[name=pw]`. Browser tests fill credential fields only with `not-real-*` values.

Known false positives, accepted (rename, or add the reviewed pragma): `tokens_per_minute = "strict-tier"` (prefer `TOKENS_PER_MINUTE_LIMIT`), `PASSWORD_INPUT = "udl-password"` (prefer `PASSWORD_FIELD`), `login = "analyst01"`, `BAD_CREDENTIALS = "..."` (prefer `BAD_CREDENTIALS_MESSAGE`).
* **Dockerfile ENV and ARG keys are judged by name**: any key that reads as a credential fails the `dockerfile` gate whatever its value, because a value set there is baked into the image. Label-style keys (`SESSION_COOKIE`, `TOKEN_URL`) are not credentials there. A reviewed exception goes in `REVIEWED_ENV_KEYS` in `tools/gates.py` with a note; it is empty. The packager runs this gate and the secret scan before it writes an archive.
* **The `read_only` gate is static.** It forbids writing verbs in the UDL package and HTTP clients anywhere else, but a verb assembled from parts would pass it. The binding control is the Phase 1 test that records every request a full run makes and fails on any verb other than GET, any body, any other host or any other path.
* **The image is built and scanned locally from 1.0.0** (Docker under WSL, grype). The local scanner's database is not the platform's, so the platform's Container Build and Container Scan stages remain the authority on the runtime image.
